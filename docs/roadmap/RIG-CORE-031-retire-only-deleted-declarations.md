## Goal

Retire a service or scheduled job because the catalogue no longer declares it, never because the applied profile did not select it. An apply must not unload a resource it never examined.

## Context

On 27 September 2026 a workstation lost every declared launchd resource at once. Nine agents — Paperclip, both mcporter transports, and six scheduled jobs — were absent from the user domain while their property lists remained on disk, and `${XDG_STATE_HOME}/rig/resources/macos.tsv` was empty. Diagnosing that outage exposed the defect this item closes.

That outage was not caused by this defect. RIG-CORE-032 owns the cause: the test suite reconciled the live machine, because most test files left the runner's `XDG_STATE_HOME` in place and the launchd adapter defaults to `/bin/launchctl` in `gui/<uid>`. This item stands on its own because the defect it found is independently live: applying any profile that selects a subset of the declared resources retires the rest.

RIG-STATE-020 and RIG-STATE-024 made profile deselection a retirement trigger, and `resource apply records managed identities and retires deselected entries` asserted exactly that by emptying a profile's resource lists while the declarations stayed in the catalogue. The defect was therefore the accepted contract, so closing it amends the specification rather than restoring it.

## Boundary

Rig owns receipt scope, staleness, and retirement dispatch. Profile deselection of tools, skills, settings, Dock layouts, and ports keeps its existing no-automatic-removal contract, unchanged here.

Catalogue deletion must still retire. Locator transfer under a new identity must still rename without retirement. A view must still load no retirement work. Withholding retirement after a selected-resource failure, the preflight boundary, and the reconciliation lock are unchanged.

Excluded: any confirmation prompt, retirement allowlist, or `--retire` flag; narrowly targeted application, which RIG-CLI-016 owns; and the host-side Paperclip recovery procedure, which the dotfiles guide owns.

## Current state

`rig_load_resource_receipt` in `src/rig/20-orchestration.bash` classified a receipt row as stale retirement work whenever `rig_selected_resource_has_locator` could not match it, and that predicate reads `RIG_SELECTED_RESOURCE_SECTIONS` — the profile-filtered selection, not the catalogue. An apply under a profile that selected few resources, or none, therefore retired every resource receipted from every other profile.

`rig_write_resource_receipt` rewrote the receipt from the same selection, so declarations the run did not select also lost their managed identity. After a narrow apply Rig could no longer observe them as its own, and a later catalogue deletion could never retire them.

Locators are already unique across the catalogue, enforced by `rig_validate_resource_locators`, so provider, kind, and locator identify a declaration unambiguously whichever profile selects it. That is what makes a catalogue-scoped test well defined.

## Review

### Delivered

The approved boundary above, in full: catalogue-scoped staleness, receipt carry-forward, the amended specification, the Decision Record, and test coverage for deletion, deselection, and the built-in launchd path. Excluded as planned: any prompt, allowlist, or `--retire` flag, and any change to targeted application.

Immutable baseline `abe812f2c48640bac54d710a990beb9bcf5c5238`. The evidence for the defect is the specification it contradicted and the test that asserted it, not the outage: the outage belongs to RIG-CORE-032, and attributing it here was the first diagnosis, corrected once the timestamps showed two of the three teardowns preceded the assembled fix.

### Change Summary

`src/rig/20-orchestration.bash` gains `rig_declared_resource_has_locator` and uses it in both `rig_load_resource_receipt` and `rig_write_resource_receipt`; `rig_selected_resource_has_locator` is now unused but retained, since removing it is unrelated cleanup. The receipt write keys carry-forward on provider, kind, and locator so a rename still transfers ownership rather than duplicating a row, and a receipt read that cannot answer the catalogue question fails the write rather than silently dropping a row.

Two decisions worth naming. Staleness compares provider, kind, and locator against declarations that support the platform, so a declaration retained for another platform still retires the local resource. Carry-forward keeps a row only while the catalogue declares it, which is safe because a failed retirement already withholds the receipt replacement, so a row awaiting retirement survives until its retirement succeeds.

No approved deviations. The changes were not committed: the user asked for the fix, not a commit.

### Outstanding concerns

The working tree mixes this change with unrelated in-flight `rig status --problems` work and with RIG-CORE-032, across `src/rig/20-orchestration.bash`, `bin/rig`, `man/rig.1`, and `tests/rig.bats`. Committing this item requires separating three changes, which is the reviewer's call.

This item does not make the suite safe to run on a machine Rig manages; RIG-CORE-032 does. A reviewer accepting this one alone should not infer that a narrow apply is now the only remaining way to lose a service.

### Post-change review

The goal is met: retirement is now a statement about the catalogue, and no apply can unload a resource outside its own selection. Scope held; no adjacent behaviour moved.

Regression risk sits in one place, the receipt carry-forward, because it is the only new write path. Rename transfer, failure preservation, atomic replacement, and the built-in launchd retirement path are all covered and green, and the read path is strictly narrower than before, so it cannot manufacture retirement work that the previous rule would not also have produced.

Ready for acceptance on the isolated evidence, with the two concerns above as the reviewer's decision: confirm the failing test belongs to the concurrent change, and choose how the commit is separated.

## Discussion

### Why the contract, not the code, was wrong

The implementation matched RIG-STATE-020 exactly, so this was not a coding slip. Profiles were given authority they were never meant to carry: every other declaration kind already removes nothing on deselection, and services and scheduled jobs were the single exception — in the one case where the consequence is a running process being killed.

### Unused predicate retained

`rig_selected_resource_has_locator` has no caller now. Removing it is unrelated cleanup, and neither ShellCheck nor the suite objects to its presence, so it stays until something else needs that file touched.
