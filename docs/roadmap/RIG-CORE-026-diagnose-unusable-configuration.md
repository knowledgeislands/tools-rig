## Goal

When Rig cannot use somebody's configuration, `rig doctor` explains what is wrong and what to do about it, rather than failing in the same way as every other command.

## Context

`rig doctor` exists to check whether Rig can operate. Given a configuration it cannot load it does neither: it emits the parse rejection and stops.

Observed against a configuration directory containing a retired `[publication.midnight-ninja]` table:

```text
$ rig doctor
rig: error: …/conf.d/10-bad.toml:1: [publication.midnight-ninja] is retired; export a view profile with rig export --profile
$ echo $?
2
```

One line, exit 2, and no diagnosis — identical to what `rig status` prints for the same input. This happened on this workstation for real: a live `90-profiles.toml` still carried a table the source had already migrated away from, and every Rig command refused until the one stale path was reapplied. The command a person reaches for when Rig has stopped working is precisely the command that cannot answer.

The message itself is good. It names the file, the line, the retired construct and the replacement. What is missing is that `doctor` treats an unloadable configuration as a reason not to run instead of as the finding it is.

## Boundary

This does not make any other command tolerate a configuration it cannot parse; a rejection is still a rejection, and `rig apply` should keep refusing. It does not add a repair or migration mode, and it does not relax the retired-construct check.

## Current state

`rig_command_doctor` in `src/rig/20-orchestration.bash` parses its own arguments, then its first substantive line is `rig_resolve_operational_plan "$profile" || return`. That call returns 2 for a configuration it cannot load, `return` propagates it, and the command ends before `rig_effective_paths`, `rig_observe_plan`, or any finding is produced. The single `rig: error:` line the reader sees is written by `rig_fail` from inside the loader, not by `doctor`.

Nothing else in the command needs configuration to be loadable. `rig_effective_paths` resolves the XDG contract, and the provider-availability and platform checks that follow are about the machine rather than the declaration. So the checks that would still be useful are precisely the ones that run after the line that refuses.

Every other command begins the same way, which is correct and stays correct: `rig_command_status`, `rig_command_apply`, and `rig_command_bootstrap` must keep refusing an unloadable configuration.

`doctor` already has a finding channel and an unhealthy status for it. `RIG_DOCTOR_FINDINGS` accumulates findings, `RIG_DOCTOR_CATALOGUE_ONLY` is kept separate from them, and `rig_outcome_report` maps a non-zero `doctor` status to `unhealthy`. A load failure reported as a finding therefore needs no new vocabulary.

## Steps

- [ ] Add a defensive load path that `rig doctor` alone uses: attempt `rig_resolve_operational_plan`, capture its status and the rejection message instead of propagating them, and continue.
- [ ] Report a captured load failure as `doctor`'s first finding, carrying the file, the line, and the reason exactly as the existing message states them, so the good message survives intact.
- [ ] Skip the configuration-dependent checks when the load failed, and run the machine-level checks — provider executable availability, effective paths, platform — against what can still be determined.
- [ ] Exit 1 rather than 2 when the only reason `doctor` cannot proceed is a configuration finding, because that is the status `doctor` already uses for an unhealthy check, and keep 2 for a rejection of the `doctor` invocation itself such as a bad `--format` value.
- [ ] Emit the same finding in the JSON projection so `--format json` reports it as a finding rather than producing no payload.
- [ ] Add Bats coverage for a configuration directory containing a retired `[publication.ID]` table: assert `rig doctor` exits 1, names the file and line in a finding, still reports provider availability, and that `rig status` and `rig apply` given the same directory still exit 2 with the unchanged message.
- [ ] Update `man/rig.1` and `docs/guides/user/commands.md` where they state `doctor`'s exit statuses.

Pass means the new Bats cases are green: given a configuration directory with a retired `[publication.ID]` table, `rig doctor` exits 1 and prints a finding naming the file, the line, the retired construct, and `rig export --profile` as the replacement, and still reports the provider and platform checks; `rig doctor --format json` emits a parseable payload containing that finding; and `rig status` and `rig apply` on the same directory are unchanged at exit 2.

## Dependencies / blocks

Nothing blocks this and it blocks nothing. It is independent of the output work: it changes what `doctor` does when it cannot load configuration, not how any report is rendered. If [RIG-CLI-018](RIG-CLI-018-one-report-renderer.md) lands first, the new finding renders through the shared renderer with no extra work.

## Documentation impact

### Decision Records

None needed, and worth stating why: strict loading everywhere else is the existing decision, and this does not weaken it. `doctor` loading defensively is a property of the one command whose job is to report on Rig's ability to operate, and the asymmetry is the point rather than an exception to be justified separately.

### Specifications

`docs/specs/state.md` changes where it states `doctor`'s findings and statuses, because an unloadable configuration becomes a finding at status 1 instead of a rejection at status 2. The rejection contract for every other command is restated unchanged.

### Guides

`man/rig.1` and `docs/guides/user/commands.md` must record that `doctor` exits 1 for a configuration it cannot load, since `docs/guides/user/commands.md` currently tells a reader that status 2 means Rig rejected configuration or profile resolution before valid work could proceed.

### Roadmap

No new follow-on work. A repair or migration mode stays out of scope and is not a deferred half of this item.

## Discussion

### What doctor would have to do differently

Report the load failure as its own finding, with the file and reason, and then continue with whatever it can still check without configuration — provider availability, executable paths, platform. That means `doctor` loading configuration defensively where every other command loads it strictly.

### Exit status

A configuration Rig cannot load is a finding, not a rejection of the `doctor` invocation, so the honest status is the one `doctor` already uses for an unhealthy check rather than 2. Settling that is part of the work.
